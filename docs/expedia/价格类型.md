# Expedia Rapid 价格类型（Rate Types）

> **定位**：查价请求该带哪些参数、响应该怎么认价的依据。回答「我们现在拿到的是哪几档价、漏了哪几档」。
> **来源**：`Tripbooking AI_technical workshop.pdf`（2026-08-04 技术研讨会，142 页）。页码为 **PDF 页序**。
> 项目范围 p4、凭证档案 p6、Shop 参数清单 p63、佣金字段 p68、价格类型 p69-79、增值服务 p80-81。
> **状态**：五种类型的取参方式与识别路径均摘自官方材料，非推测。本服务的接入现状见 §5，
> 其中「会员价」「移动端价格」两档目前拿不到。

---

## 1. 先分清三件不同的事

讨论「价格」时最容易串的三个维度。它们**不是三个可自由组合的轴，而是层层收窄**：
前一个限定后一个的可选范围。

| | 维度 | 问的问题 | 取值 | 我们能不能选 |
|---|---|---|---|---|
| ① | **凭证车道** | 我们以什么身份问价？ | B2C 档案 / B2B 档案（见 §4） | 能，靠配置 |
| ② | **价格类型** | 拿到的是哪一档价？ | 单卖 / 打包 / 会员 / 移动端 / 高利润（见 §3） | 能，靠请求参数 |
| ③ | **付款方式** | 谁向旅客收钱？ | 见 §1.1 | **不能**，每条报价自带 |

收窄关系具体有三处：

| 谁限制谁 | 表现 | 依据 |
|---|---|---|
| ① → ② | 移动端价格**仅 B2C** 可得 | p74，标题即 "Mobile Deals (B2C Only)" |
| ① → ② | 打包价**仅 B2B** 可得 | p72，"Only available for B2B channel" |
| ② → ③ | 高利润价（OD）**仅支持** Expedia Collect | p76 |

**车道选错，下面两层跟着全歪**——这正是「两条车道参数不可混用」的实际后果：
它不产生报错，而是换掉了整个可售卖的价格集合。

### 1.1 付款方式（p70）

| | Expedia Collect（预付） | Property Collect（到店付） |
|---|---|---|
| 谁向旅客收钱 | Expedia Group 或合作方 | 酒店 |
| 谁向谁开票 | 酒店开票给 Expedia Group | Expedia Group 开票给酒店 |
| 何时付 | 下单时付（通常立即） | 到店付（通常后付） |

**⚠️ 我方合同下的实际形态是第三种，不是上表任一列。**

我方 `billing_terms=EAC`，而 p86「Booking API (EAC)」页出现的是 **`affiliate_collect`**
（我方代收款）——**钱由我们向旅客收**，既非 Expedia 收也非酒店收。

「预付」在**旅客视角**成立（先付款后入住），但在**谁是收款方**这一层，我方是
affiliate_collect。两个词不可混用，否则下单请求体会照错模型实现。
该项在 `../expedia-booking-contract.md` §5 已列为待向 EPS 确认，未确认前不实现支付部分。

### 1.2 本服务的策略：只做预付

**对外只提供预付形态**（房费先收）。

⚠️ 两点必须说清，否则前端与客服口径会错：

1. **预付 ≠ 旅客到店零支付。** 即便房费整单预付，`property_fees`（resort fee、
   强制杂费）仍由旅客**到店支付**。代码已处理：`storePayPrice` / `storePayCurrency`
   取自 `totals.property_fees`。对外口径应为「**房费预付，酒店杂费到店付**」。
2. **该策略目前是期望，不是保证。** 代码未做任何筛选或校验，见 §5.4。

| | 单卖价<br>Standalone | 打包价<br>Package | 会员价<br>MOD | 移动端价格<br>Mobile | 高利润价格<br>Distribution (OD) |

## 3. 每一档怎么取、怎么认

「怎么取」= 请求里要带什么；「怎么认」= 响应里从哪个字段判断这条报价属于该档。

### 3.1 单卖价 Standalone（p72）

- **取**：`sales_environment=hotel_only`
- **认**：即默认形态，无需额外标志

### 3.2 打包价 Package（p72）

- **取**：`sales_environment=hotel_package`
- **认**：`rates.sale_scenario.package = true`
- ⚠️ PDF 原文：**「Only available for B2B channel」**（仅 B2B 车道可用）
- 用途：必须与其他旅行组件一起售卖

### 3.3 会员价 MOD（p73）

- **取**：`rate_option=member`
- **认**：`rates.sale_scenario.member = true`
- ⚠️ **展示约束（原文）**：「These rates should be shown **only** to users who have logged into the site」
  —— 中文页同步写「只能展示给登录后的会员」。这是硬约束，不是建议。

### 3.4 移动端价格 Mobile（p74）

标题原文为 **「Mobile Deals (B2C Only)」**。

- **取**：两个参数一起
  - `sales_channel = mobile_app`
  - `include = sale_scenario.mobile_promotion`
- **认**：`rates.sale_scenario.mobile_promotion = true`

**这一条是 `sales_channel` 的实际作用所在**：它不是一个供记录的标签，而是决定 Expedia
要不要把这一档折扣价算进返回结果。发 `agent_tool` 就拿不到移动端折扣价。

### 3.5 高利润价格 Optimised Distribution / OD（p76-77）

- **取**：无需额外请求参数，随 Shop 响应下发
- **认**：`rates.sale_scenario.distribution = true`
- 来源：部分酒店集团与 Expedia 签长约，给出高佣金、常为 Expedia 独有的批发价
- 售卖范围（原文）：可在**获批的 B2C 站点线上**售卖，也可通过**获批的 agent tool 线下**售卖；
  单卖与打包两条路径皆可，**但仅限 Expedia Collect**

**PDF 给的排序建议（p77）** —— 属商业优化建议，非强制：

- 若可退性相同而价格相同，选 OD
- 若非 OD 那条多一个非关键设施（如免费停车）但价格相同，仍优选 OD
- 若 OD 与非 OD 价差 ≤ 2%，优选 OD
- 或直接把高毛利 OD 排在前面

## 4. 车道决定你能拿到哪几档

凭证档案（见 `../expedia-booking-contract.md` §1）不只是身份标记，它**限制了可取的价格类型**：

| 价格类型 | B2C 档案 | B2B 档案 |
|---|---|---|
| 单卖价 | ✅ | ✅ |
| 打包价 | 以 cross-sell 形态 | ✅ 以 package 形态（PDF：Package 仅 B2B） |
| 会员价 | ✅（`rate_option` 可取 `member`/`cross_sell`） | ✅（`rate_option` 仅 `member`） |
| 移动端价格 | ✅ 需 `sales_channel=mobile_app` | ❌ 标题即写 B2C Only |
| 高利润价格 | ✅ 获批站点 | ✅ 获批 agent tool |

由此可见：**换车道会改变能拿到的价格集合**，而不只是换一组标识字符串。

### 4.1 实测：混用会把报价抬高约 18%

以下是实打 `test.ean.com` 的结果，不是推断。同一把 DEV key、同一家酒店
（property 11775754）、同一批日期（2026-10-04 至 10-08）、`sales_environment=hotel_only`，
三次调用结果一致。

**先说前提**：两套档案共用同一把 API key，Expedia **不校验**你送来的四项参数是否属于
同一套档案。四种组合全部返回 HTTP 200，没有任何错误或警告。

**混用有方向性。** 把 `sales_channel` 单独改动，在两条车道上后果完全不同：

| 组合 | 报价条数 | 含税价（CNY） |
|---|---|---|
| B2B 档案 + `agent_tool`（正确） | 5 | 100.92 / 104.36 / 117.66 / 117.89 ×2 |
| B2B 档案 + `mobile_app`（混用） | 5 | **与上一行逐条相同** |

B2B 车道上混用无后果 —— 移动端折扣本就是 B2C 专属（§3.4），B2B 档案上这个参数没有着力点。

| 组合 | 报价条数 | 含税价（CNY） |
|---|---|---|
| B2C 档案 + `agent_tool`（混用） | 6 | 85.38 / 88.20 / 99.17 / 99.44 ×3 |
| B2C 档案 + `mobile_app`（正确） | 7 | **72.49** / 84.03 ×2 / 84.27 ×2 / 99.44 |

B2C 车道上后果是钱。按报价 ID 逐条对齐（同一间房、同一个 rate plan）：

| 报价 ID | 混用（错） | 正确 | 贵了 |
|---|---|---|---|
| 276305852 | 88.20 | 74.95 | 17.7% |
| 276305862 | 99.44 | 84.27 | 18.0% |
| 276321197 | 99.17 | 84.03 | 18.0% |
| 276321198 | 99.44 | 84.27 | 18.0% |
| 276321199 | 85.38 | 72.49 | 17.8% |

另有两条报价（`276305863`、`276358144`）在混用时根本取不到。

**净结果**：若配置持 B2C 档案而 `sales_channel` 停在 B2B 的值，我们会按贵约 18% 的价格
对外报价，并少拿两条报价。Expedia 返回 200，不报错、不告警 —— 这个错配只能靠拿两套参数
各打一次再逐条对价才能发现。

这就是「两条车道参数不可混用」的实质后果，也是 `ExpediaContractProfile` 在启动期
校验四项是否成组的理由。

## 5. 本服务现状

### 5.1 查价请求实际发出的参数

`QueryProductAccess.request()` 构造的 body：

| 参数 | 值 | 来源 |
|---|---|---|
| `property_id` `checkin` `checkout` `currency` | 逐单 | 上游请求 |
| `language` | `zh-CN`（默认） | 构造参数 |
| `country_code` | `CN` | **代码写死** |
| `sales_environment` | `hotel_only` / `hotel_package` | 逐单 |
| `rate_plan_count` | `250` | **代码写死** |
| `sales_channel` | `agent_tool` | **代码写死** |
| `billing_terms` `payment_terms` `partner_point_of_sale` | B2B 档案值 | 配置 `expedia.*` |

### 5.2 没有发出的参数

| 参数 | 后果 |
|---|---|
| `rate_option` | 拿不到**会员价**。PDF 的 B2B 档案明确写 `Rate_option - member`，即 Expedia 期望我方发送 |
| `include=sale_scenario.mobile_promotion` | 移动端价格的两个必要条件之一缺失 |
| `supply_source` | 官方 availability 示例带 `supply_source=expedia`，我方未发；影响未验证 |
| `marketing_fee_incentives` | 拿不到短期促销（XLR）的加佣信息，见 §6.2 |
| `amenity_category` | 未做设施筛选（p79）。属可选优化，非缺陷 |

### 5.3 响应模型只认三个标志

`QueryPriceResponse.Sale_scenario` 目前只有三个布尔字段：

```java
private boolean member;
private boolean corporate;
private boolean distribution;
```

- `distribution` 已被使用：`ProductRespDTO.distribution` 透传给上游
- `member` 已建模但未被消费 —— 因为根本没发 `rate_option`，不会有为 true 的报价
- **`package` 与 `mobile_promotion` 两个字段未建模**，即便发了对应参数也认不出来
- `corporate` 本次所据 PDF **完全未提及**。该字段来自 Rapid API 自身的 schema，
  其含义无法由本材料确定，需另找依据

### 5.4 付款方式这一维：既不筛也不看

§1.2 的「只做预付」是策略，但**代码中没有任何一处保证它**：

| 可用手段 | 现状 |
|---|---|
| 请求发 `filter` 筛掉到店付 | ❌ 从未发送 |
| 读报价的 `merchant_of_record` 拒掉非预付 | ❌ `QueryPriceResponse.Rates` 中已建模，**零消费** |
| 酒店级 `business_model` | ✅ 已落库：`ExpediaPropertyDocument.BusinessModel(expediaCollect, propertyCollect)`，但未用于筛选 |

后果：**若 Expedia 返回一条 property_collect 报价，本服务会将其当作预付售出。**

现有证据仅一条样本——沙箱实测下单后反查，`rooms[].rate.merchant_of_record` 为 `expedia`
（见 `../expedia-booking-contract.md` §7.1）。一条样本不构成保证。

补充：本 PDF 中 `filter` 仅出现过 `property_collect` 一个取值，**未出现「只要预付」的取值**。
若要靠 filter 实现，须先确认该取值是否存在。

若要把策略变成保证，可选动作（属行为变更，应单独评估与实测，不应与参数收口混做一次改动）：

- 查价／验价后读 `merchant_of_record`，非预付报价直接丢弃并记日志
- 或在请求侧筛选（前提是确认存在对应的 filter 取值）

## 6. 佣金相关字段

### 6.1 GP 与 MF（p68）

Shop 与 Price Check 两个响应里都有：

| 字段 | 含义 |
|---|---|
| `gross_profit`（GP，毛利） | 本单的预计总收益，Expedia Group 再与我方分成 |
| `marketing_fee`（MF，佣金） | **我方在本单可得的预计算金额**，依商业协议／销售成本估算 |

本服务只取 `marketing_fee`，未下发时记 0。旧的 `gross_profit × 0.525` 估算已在
`875b258` 中删除 —— 那是上一份公司合同的算法。

### 6.2 短期促销 Accelerator / XLR（p75、p78）

- 酒店在特定入住期临时提高佣金比例，**在全部单卖价上都能看到该促销**
- 取法：请求中带 `rooms.rates.marketing_fee_incentives`
- 认法：响应 `marketing_fee_incentives` 字段给出受影响的入住日期
- 与 OD 的区别：XLR 是**临时**加佣，OD 是**长约**高佣价

## 7. 展示约束（合规向）

这几条是 PDF 明确写的展示要求，落到前端与对外报价时须遵守：

- **会员价只能给已登录用户看**（p73）
- **增值服务 VAP**（p80-81）：入住期间的赠品／权益（如免费主题公园门票），
  可标为 FREE add-on。它是**季节性、绑定具体费率**的，与永久设施（免费 WiFi 之类）不同，
  应醒目展示并配赠礼类图标
- **划线价**（p81）三个字段各有含义，不可混用：
  - `strikethrough` —— 不含任何税费的折前价
  - `inclusive_strikethrough` —— 含全部税费的折前价，适合 UI 上做划线
  - `property_inclusive_strikethrough` —— 含税费**与酒店杂费**的折前价，
    用于展示含酒店杂费总价时的划线
- **优惠券折后价不得对外宣传**（p133-134）：例如不可在 Meta 渠道展示「原价减券后」的价格；
  券应作为附加组件呈现，而非价格折扣
